HIGH 2.1. Release 빌드 R8/ProGuard 비활성화

영향 파일

파일라인
app/build.gradle.kts20-25
sdk/bmf-sdk-core/build.gradle.kts17-22
sdk/bmf-sdk-auth/build.gradle.kts17-22
sdk/bmf-sdk-pm/build.gradle.kts17-22
sdk/bmf-sdk-pop/build.gradle.kts17-22

현재 코드

// app/build.gradle.kts:20-25 (SDK 모듈 4개도 동일 패턴)
buildTypes {
    release {
        isMinifyEnabled = false
        proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
    }
}

무엇이 문제인가

  • isMinifyEnabled = false → R8(난독화·축소·최적화)이 동작하지 않는다.
  • proguardFiles(...) 라인은 minify가 꺼져 있으면 읽히지 않는다. "선언만 되어 있고 실제로는 무력화된" 상태.
  • app/proguard-rules.pro 내용도 # Add project specific ProGuard rules here. 한 줄뿐 — 실질적 keep/strip 규칙 0개.

왜 위험한가 — 공격 시나리오

[1] 공격자: 운영 APK 또는 AAR 파일 확보 (Play Store / Maven / 사내 배포) [2] jadx-gui apk.apk → 소스 트리 자동 복원 → BmfSdkAuth.init(), BmfSdkPm.charge(...) 등 메서드명·시그니처가 원문 그대로 노출 [3] strings classes.dex | grep -Ei "secret|key|token|http" → 향후 박힐 상수·엔드포인트 추출 [4] Frida hook com.bmf.sdk.auth.BmfSdkAuth.init "{ onEnter: ... }" → 클래스/메서드명을 그대로 사용 가능, 인증·결제 흐름 후킹 진입 장벽 0 [5] 우회 빌드 / 우회 패치 / 부정 사용 영상 유출 → 평판 손상
R8 난독화는 만능이 아니지만(상수 노출은 키스토어/Play Integrity 등 별도 통제 필요), 있고/없고의 차이가 공격자 작업 시간을 시간 단위에서 분 단위로 줄여준다. 토큰·결제 도메인 SDK의 디폴트로는 부적절.

수정 가이드 — 단계별

Step 1. SDK 라이브러리 모듈 4개의 build.gradle.kts에서 release 블록 정리

라이브러리 모듈은 AGP 8.x부터 자체 release.isMinifyEnabled 효과가 거의 없다 — R8는 호스트 앱이 minify를 켤 때 라이브러리까지 함께 처리한다. 따라서 라이브러리 측 책임은:

  1. consumer-rules.pro에 반드시 살아남아야 할 keep 규칙을 박는다 (§2.2).
  2. 라이브러리 자체 빌드 시 minify 옵션은 제거해도 무방하다.
// sdk/bmf-sdk-{core,auth,pm,pop}/build.gradle.kts — after
android {
    // ...
    buildTypes {
        release {
            // 라이브러리 모듈은 minify 비활성. R8 책임은 호스트 앱에 위임.
            // 의미 없는 라이브러리 측 proguardFiles 선언 제거.
            consumerProguardFiles("consumer-rules.pro")
        }
    }
}
consumerProguardFiles는 defaultConfig 또는 release 둘 다에서 지정 가능. 현재 defaultConfig에 있으면 그대로 두고, buildTypes.release의 proguardFiles(...) 줄만 제거하면 된다.
Step 2. app/build.gradle.kts에서 release 빌드 minify·shrink 활성화
// app/build.gradle.kts — after
android {
    // ...
    buildTypes {
        debug {
            isDebuggable = true
            isMinifyEnabled = false
            applicationIdSuffix = ".debug"
            versionNameSuffix = "-debug"
        }
        release {
            isDebuggable = false
            isMinifyEnabled = true
            isShrinkResources = true
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"
            )
            // signingConfig 는 §2.6 에서 정의
        }
    }
}

HIGH 2.2. consumer-rules.pro가 전부 빈 파일

영향 파일

파일크기
sdk/bmf-sdk-core/consumer-rules.pro0 bytes
sdk/bmf-sdk-auth/consumer-rules.pro0 bytes
sdk/bmf-sdk-pm/consumer-rules.pro0 bytes
sdk/bmf-sdk-pop/consumer-rules.pro0 bytes

현재 코드

// sdk/bmf-sdk-*/build.gradle.kts:14
defaultConfig {
    // ...
    consumerProguardFiles("consumer-rules.pro")   // 파일은 비어 있음
}
# sdk/bmf-sdk-*/consumer-rules.pro
(empty)

무엇이 문제인가

  • consumerProguardFiles는 AAR 안에 동봉되어 호스트 앱의 R8 단계에 자동 병합되는 규칙 파일이다. SDK가 "호스트 앱이 minify를 켜도 부서지지 않을 보호 정책"을 호스트에 강제 전달하는 유일한 채널.
  • 현재 4개 모듈 모두 빈 파일 → 호스트 앱이 minify를 켜는 순간:
    • 공개 API(BmfSdk.initialize 등)에 호스트가 의존하는 메서드/필드는 살아 있지만, 향후 추가될 리플렉션 기반 직렬화(Gson/Moshi), Parcelable, JNI symbol, @JavascriptInterface 메서드, Coroutine 직렬화 등은 모두 R8에 의해 제거되어 NoSuchMethodError/ClassNotFoundException 발생 가능.
    • 결과적으로 SDK 통합 가이드가 "호스트 앱은 minify를 끄세요"로 변질될 위험 → 생태계 전체 보호 수준 하락.
  • 결제·인증 SDK 입장에서 이는 단순 호환성 이슈가 아니라 보안 토대 약화다.

MEDIUM 2.5. BmfSdk.initialize()의 Context 컨트랙트 부재

영향 파일

sdk/bmf-sdk-core/src/main/java/com/bmf/sdk/BmfSdk.kt:6-19, app/src/main/java/com/bmf/sdk/sample/MainActivity.kt:13

현재 코드

// BmfSdk.kt
object BmfSdk {
    private const val TAG = "BmfSdk"
    private var isInitialized = false                  // ← @Volatile 없음

    fun initialize(context: Context) {                  // ← context 사용 안 함
        if (isInitialized) {                            // ← race condition 가능
            Log.w(TAG, "BmfSdk is already initialized.")
            return
        }
        isInitialized = true
        Log.d(TAG, "BmfSdk initialized.")
    }
}
// MainActivity.kt:13
BmfSdk.initialize(this)   // ← Activity 컨텍스트 그대로 전달 (안티패턴)

무엇이 문제인가

  1. Thread-safety 부재: isInitialized가 일반 var. 호출자가 동시 호출하면 race로 부분 초기화 가능.
  2. Context 정규화 없음: 호출자가 Activity / Service / Receiver / Application 무엇이든 그대로 받음. 향후 EncryptedSharedPreferences / Keystore 핸들을 만들 때 Activity Context로 만들면 lifecycle 종속이 어긋남.
  3. 샘플이 잘못된 사용을 박제: MainActivity.kt:13의 BmfSdk.initialize(this)는 SDK 사용자가 그대로 복사할 첫 자료다.
  4. 초기화 순서 정책 부재: BmfSdkAuth.init() 등 자식 SDK가 BmfSdk.initialize() 호출 없이 호출되어도 막지 못함.

왜 위험한가 — 공격 시나리오 (간접)

[1] 호스트 앱 개발자: BroadcastReceiver.onReceive() 안에서 BmfSdk.initialize(context) 호출 [2] Receiver context 가 SDK 깊숙이 흘러감 (10초 후 소멸) [3] SDK 가 EncryptedSharedPreferences("secure_prefs") 핸들 생성을 지연 시도 [4] 호스트가 multi-process(":bmf") 로 분리되어 있어 동일 prefs 가 프로세스마다 다르게 보임 → 토큰 일부 유실 [5] 키 무효화(KeyPermanentlyInvalidatedException) 가 잘못 처리되어 "토큰 없음" → 익명 세션으로 fallback → 인가 우회

Step 1. BmfSdk를 thread-safe + applicationContext 정규화로 재작성
// sdk/bmf-sdk-core/src/main/java/com/bmf/sdk/BmfSdk.kt — after
package com.bmf.sdk

import android.app.Application
import android.content.Context
import com.bmf.sdk.internal.BmfLog

object BmfSdk {
    private const val TAG = "BmfSdk"

    @Volatile
    private var appContext: Context? = null
    private val lock = Any()

    /**
     * BMF SDK 를 초기화한다.
     *
     * 호출 위치:
     *  - 권장: [Application.onCreate] 또는 androidx.startup Initializer
     *  - 비권장: Activity/Service/Receiver 의 일시적 컨텍스트
     *
     * 멀티 호출은 안전하며 두 번째 이후 호출은 무시된다 (멱등).
     *
     * @param context any Context — 내부에서 [Context.getApplicationContext] 로 정규화한다.
     */
    @JvmStatic
    fun initialize(context: Context) {
        if (appContext != null) return
        synchronized(lock) {
            if (appContext != null) return
            val app = requireNotNull(context.applicationContext) {
                "BmfSdk.initialize: context.applicationContext is null. " +
                "Pass an Application or use applicationContext."
            }
            appContext = app
            BmfLog.d(TAG) { "BmfSdk initialized." }
        }
    }

    /** SDK 내부 모듈이 컨텍스트를 얻는 유일한 경로. */
    @JvmStatic
    internal fun requireContext(): Context = appContext
        ?: error("BmfSdk.initialize(context) must be called before any SDK API is used.")

    /** 테스트 용도. production 호출 금지. */
    @JvmStatic
    internal fun resetForTesting() {
        synchronized(lock) { appContext = null }
    }
}

샘플 매니페스트 (현재 사실상의 표준 가이드 역할) — app/src/main/AndroidManifest.xml:9-16

현재 코드

<activity
    android:name=".MainActivity"
    android:exported="true">                <!-- LAUNCHER 라 정상이지만, 정책 가이드 없음 -->
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
</activity>

무엇이 문제인가

  • 런처 Activity의 exported="true" 자체는 필수.
  • 다만, SDK가 향후 다음과 같은 Activity를 추가할 가능성이 높다:
    • OAuth 콜백 Activity (bmf://auth/callback 등)
    • 결제 결과 Activity (PG 리턴)
    • 팝업/딥링크 진입점
  • 이때 정책 없이 exported="true"를 추가하면 임의의 외부 앱이 인텐트로 진입 가능 → 토큰/주문번호 주입 / intent redirection 가능.

import androidx.security.crypto.MasterKey

class SecureTokenStore(context: Context) {
    private val prefs = run {
        val masterKey = MasterKey.Builder(context)
            .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
            // 결제 등 강한 보호가 필요하면 true + Biometric
            .setUserAuthenticationRequired(false)
            .build()

        try {
            EncryptedSharedPreferences.create(
                context,
                "bmf_sdk_secure_prefs",
                masterKey,
                EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
                EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
            )
        } catch (e: KeyPermanentlyInvalidatedException) {
            // 단말 PIN 변경/Biometric 갱신 시 Keystore 키가 무효화될 수 있음
            // → 기존 prefs 삭제 후 재생성
            context.deleteSharedPreferences("bmf_sdk_secure_prefs")
            // 재귀 호출보다는 reset 후 별도 entry point 사용 권장
            throw e
        }
    }

    fun saveAccessToken(token: String) {
        prefs.edit().putString(KEY_ACCESS_TOKEN, token).apply()
    }
    fun accessToken(): String? = prefs.getString(KEY_ACCESS_TOKEN, null)

    fun clear() = prefs.edit().clear().apply()

    companion object { private const val KEY_ACCESS_TOKEN = "access_token" }
}

3.6. Deep Link — App Links + state nonce

object AuthStateNonce {
    private const val KEY_NONCE = "bmf_auth_nonce"
    private val secureRandom = SecureRandom()

    fun issue(prefs: SharedPreferences): String {
        val bytes = ByteArray(32).also(secureRandom::nextBytes)
        val nonce = Base64.encodeToString(bytes, Base64.URL_SAFE or Base64.NO_WRAP)
        prefs.edit().putString(KEY_NONCE, nonce).apply()
        return nonce
    }

    fun consume(prefs: SharedPreferences): String? {
        val nonce = prefs.getString(KEY_NONCE, null)
        prefs.edit().remove(KEY_NONCE).apply()
        return nonce
    }

    fun verify(prefs: SharedPreferences, received: String?): Boolean {
        val expected = consume(prefs) ?: return false
        // timing-safe equality
        return MessageDigest.isEqual(
            expected.toByteArray(Charsets.UTF_8),
            received?.toByteArray(Charsets.UTF_8) ?: return false
        )
    }
}
