이 URL 은 userInfo["fcm_options"]["image"] / userInfo["image"] / userInfo["senderProfileImage"] 즉 푸시 발신자가 자유롭게 지정 가능한 페이로드 다.

이유 (왜 취약한가)

  • 공격 시나리오:
    1. APNs 토큰 또는 FCM 발신 권한이 유출/오용된 상황(또는 잘못된 백엔드 게이트웨이 설정)에서 공격자가 fcm_options.image 에 임의 URL 을 넣어 푸시를 발송.
    2. NSE 가 다음을 수행한다:
      • URL scheme/host 검증 없음 → http://attacker.example/probe?token=... 같은 평문 HTTP 도 받아옴 → ATS 가 NSE 에도 적용되지만 NSAllowsArbitraryLoadsInWebContent 가 true 인 메인 타깃과 별개로 NSE Info.plist 에는 ATS 키가 없으므로 기본 ATS 가 적용되어 평문은 거부됨 (1차 방어). 단 HTTPS 인 한 임의 도메인 호출은 허용.
      • 응답 파일을 NSTemporaryDirectory() 에 UUID + suggestedExtension 으로 저장.
      • suggestedExtension = url.pathExtension 을 그대로 사용 — image.html 같은 path 에 대해 <uuid>.html 로 저장된다. UNNotificationAttachment 생성은 식별된 UTI 기준이라 첨부에 실패할 가능성이 높지만, 디스크 상 임시 파일은 남는다.
    3. 더 큰 위험은 발신자 아바타(senderProfileImage) 다운로드 경로 — downloadImageData 가 response 검증 없이 Data 만 회수, UIImage(data:) 가 성공하면 그대로 INImage 로 시스템 인터랙션에 donate. iOS 가 거대한 이미지(예: pixel bomb)나 변조된 이미지를 디코드하는 과정에서 NSE 메모리 한도(24MB) 초과로 silent kill. 결과적으로 합법 푸시 전달이 침묵 실패 하는 DoS 가 발생.
    4. 부수적으로 임의 URL 호출 = 콘텐츠 트래킹 픽셀 로도 동작 (이메일 트래킹과 동일 원리). 발신자가 특정 사용자의 푸시 수신/오프라인 여부를 timing 으로 추론 가능.
  • 영향 범위: 모든 푸시 수신자. DoS / 메타데이터 누설 / 외부 트래픽 유발.
  • 관련 표준:
    • OWASP MASVS-PLATFORM-3 (push payload trust)
    • KISA "모바일 앱 시큐어 코딩 가이드 — 입력값 검증" §3.2
    • Apple "Modifying Content in Newly Delivered Notifications" — attachment URL 신뢰성 책임은 앱 측.

private static let allowedImageHosts: Set<String> = [
    // 실제 푸시 이미지를 제공하는 CDN 만 등록 (예시)
    "cdn.flozip.com",
    "media.bmf.com",
    "firebasestorage.googleapis.com",
]

private static func sanitizedImageURL(_ raw: String) -> URL? {
    guard let url = URL(string: raw),
          let scheme = url.scheme?.lowercased(),
          scheme == "https",                                     // HTTPS 강제
          let host = url.host?.lowercased(),
          allowedImageHosts.contains(host) else {                // host whitelist
        return nil
    }
    // 확장자도 통제 — 알려진 이미지 확장자만 허용. 그 외는 `.img` 강제로 신뢰 가능 영역으로 좁힘.
    return url
}

private func downloadImageAttachment(
    from userInfo: [AnyHashable: Any],
    completion: @escaping (UNNotificationAttachment?) -> Void
) {
    guard let urlString = imageUrl(from: userInfo),
          let url = Self.sanitizedImageURL(urlString) else {
        completion(nil)
        return
    }
    // 응답 검증 — content-type 확인 + 크기 cap (예: 2MB) 두 가지 추가.
    let task = URLSession.shared.downloadTask(with: url) { tempLocation, response, _ in
        guard let tempLocation,
              let http = response as? HTTPURLResponse,
              (200..<300).contains(http.statusCode),
              let mime = http.mimeType, mime.hasPrefix("image/"),
              http.expectedContentLength <= 2 * 1024 * 1024 else {
            completion(nil)
            return
        }
        // 확장자는 mime 으로 정해서 path 의 영향력을 제거.
        let ext = (mime == "image/png") ? "png" : "jpg"
        let dest = URL(fileURLWithPath: NSTemporaryDirectory())
            .appendingPathComponent("\(UUID().uuidString).\(ext)")
        do {
            try FileManager.default.moveItem(at: tempLocation, to: dest)
            let attachment = try UNNotificationAttachment(identifier: "image", url: dest, options: nil)
            completion(attachment)
        } catch {
            completion(nil)
        }
    }
    task.resume()
}

추가로 downloadImageData 에도 동일한 sanitize + content-type + 길이 cap 을 적용. NSE Info.plist 에 ATS 키가 명시적으로 없는 상태(메인앱은 NSAllowsArbitraryLoadsInWebContent: true 가 설정되어 있지만 NSE 와 별개) 라도, 앱 측 검증을 명시 하는 것이 defense-in-depth.

  • 추가 검토할 호출자/주변 코드:
    • 백엔드 푸시 발송 게이트웨이가 사용자 입력(예: 채팅 메시지 첨부 이미지)을 그대로 페이로드에 싣는지 확인. 그렇다면 발송 단계에서도 URL 검증이 필요.
    • applyCommunicationIntent 의 INPerson.displayName = senderName — senderName 길이 제한·이모지/제어문자 sanitize 가 백엔드/앱 어느 쪽에서도 안 되어 있다면 시스템 인터랙션 UI 가 비정상 표시될 수 있음.

MediumUniversal Link 외부 URL 에 SFSafariViewController scheme 검증 누락 (보안)

위치: Sources/ios-bmf-sdk-product/App/Deeplink/UniversalLinkHandler.swift:71-89, Sources/ios-bmf-sdk-product/App/Deeplink/SafariView.swift:22-33

취약 코드

// UniversalLinkHandler.swift
private func process(url: URL) async {
    guard !Task.isCancelled else { return }
    do {
        guard try await BMFSDK.stage(byURL: url) == nil else {
            return
        }
        guard !Task.isCancelled else { return }
        // 외부 도메인 → 외부 브라우저
        pendingExternalURL = IdentifiableURL(url)
    } catch {
        // 네트워크 에러 시에도 외부 브라우저로 fallback
        pendingExternalURL = IdentifiableURL(url)
    }
}

// SafariView.swift
func makeUIViewController(context: Context) -> SFSafariViewController {
    SFSafariViewController(url: url)   // ← url scheme 검증 없음
}

이유 (왜 취약한가)

  • SFSafariViewController(url:) 는 http/https 가 아닌 스킴(file://, javascript:, data: 등)으로 초기화하면 런타임에 NSInvalidArgumentException 으로 크래시한다. 또한 일부 OS 버전에선 file:// URL 을 받아 로컬 파일 미리보기로 동작하는 케이스가 있었다 (history).
  • Universal Link 경로는 시스템이 https 만 전달하지만, process(url:) 에 들어오는 URL 은 외부에서 유발될 수 있고(Custom URL Scheme → 향후 라우팅 확장 시 재사용 가능성), BMFSDK.stage(byURL:) 가 throw 한 경우(catch)에도 무조건 pendingExternalURL 로 회부된다 — 즉 scheme == https 라는 사전 조건이 코드 상에 명시되지 않은 상태.
  • 공격 시나리오: 잘못된 입력(메시지의 악의적 링크, 브라우저 리다이렉트 체인 등)으로 비-http(s) URL 이 도달하면 (1) SFSafariVC 가 크래시, (2) pendingExternalURL 이 set 됐다가 consume 되지 않아 sheet 가 무한 재발화 가능.
  • OWASP MASVS-PLATFORM-3 / KISA "외부 자원 접근 시 URL 스킴 검증" 위배 (defense-in-depth).

수정안

// UniversalLinkHandler.swift
private func process(url: URL) async {
    guard !Task.isCancelled else { return }
    // SFSafariViewController 는 http/https 만 받는다 — 그 외는 무시.
    guard let scheme = url.scheme?.lowercased(),
          scheme == "http" || scheme == "https" else {
        return
    }

    do {
        guard try await BMFSDK.stage(byURL: url) == nil else { return }
        guard !Task.isCancelled else { return }
        pendingExternalURL = IdentifiableURL(url)
    } catch {
        guard !Task.isCancelled else { return }
        pendingExternalURL = IdentifiableURL(url)
    }
}

이유 (왜 취약한가)

  • Configuration.appStoreID 는 Info.plist 의 AppStoreID 빌드 설정에서 주입된다 ($(APP_STORE_ID)). xcconfig 가 신뢰원이므로 자체 변조는 어렵지만, bundle 변조(deploy 후 plist 재서명) 케이스에서 임의 path 가 들어가 apps.apple.com/app/id<arbitrary> 로 우회 가능. URL 자체가 apps.apple.com 도메인이라 피해는 제한적 (외부 임의 URL 은 아님).
  • exit(0) — Apple HIG 에서 권장되지 않는 패턴 (앱이 crash 처럼 보임). Critical 이슈는 아니지만 사용자가 앱을 "강제 종료당함" 으로 인지하면 OS 단위 신뢰 저하 + 일부 MDM 환경에선 "crash 카운트" 로 집계.
  • remoteURL 인 https://flo-zip.web.app/appVersion.json 이 평문 코드에 박혀 있고, 이 URL 자체는 HTTPS 라 OK 지만, Firebase Hosting 의 보안 설정(예: 호스트 도메인 takeover 방지, project deletion 후 도메인 재할당 등)이 환경팀에서 모니터링되고 있는지 확인 필요. 만약 이 도메인이 미사용으로 회수되면 공격자가 같은 web.app 이름을 점유해 임의 JSON 으로 강제 업데이트 / 강제 종료 트리거 가능. (isVersion(_:lessThan:) 가 let lhsParts = lhs.split... map { Int($0) ?? 0 } 라 강제 999.999.999 같은 값으로 항상 force-update 트리거 가능)

수정안

  1. openAppStore 의 Configuration.appStoreID 가 숫자만 인지 검증: 
    func openAppStore() {
    let id = Configuration.appStoreID
    guard !id.isEmpty, id.allSatisfy(\.isNumber) else { return }
    guard let url = URL(string: "https://apps.apple.com/app/id\(id)") else { return }
    UIApplication.shared.open(url)
}
  2. exit(0) 대신 UIApplication.shared.perform(#selector(NSXPCConnection.suspend)) 같은 HIG 친화적 방식 — 혹은 force-update 알럿을 dismiss 불가로 두고 사용자가 직접 종료하게 유도.
  3. remoteURL JSON 의 integrity 검증 — 응답에 서명을 포함하거나, 응답이 일정 schema 를 벗어나면 거부. 최소한 minVersion/version 이 빈 문자열이거나 비현실적 값(예: major > 99) 인 경우 무시.
  • 추가 검토: Firebase Hosting 호스트(flo-zip.web.app) 의 소유권/만료 일정을 인프라팀이 추적 중인지.

    static func sweep() {
        let tmp = FileManager.default.temporaryDirectory
        let prefixes = ["quick-audio-", "quick-video-"]
        if let files = try? FileManager.default.contentsOfDirectory(at: tmp, includingPropertiesForKeys: nil) {
            for url in files where prefixes.contains(where: { url.lastPathComponent.hasPrefix($0) }) {
                try? FileManager.default.removeItem(at: url)

        }
    }
