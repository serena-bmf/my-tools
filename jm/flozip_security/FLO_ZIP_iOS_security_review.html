01 요약 (Executive Summary)

전반적 보안 위생: 양호 — Critical/High 미발견

FLO ZIP iOS 빌드를 디컴파일하여 OWASP MASVS/MASTG 기준으로 정적 점검했습니다. 빌드는 미암호화(cryptid=0)라 전체 분석이 가능했고, 치명적(Critical)·높음(High) 등급 취약점은 발견되지 않았습니다. 중점 항목인 중요정보 하드코딩에서 실제 유출 시크릿은 확인되지 않았습니다(Firebase 키만 존재 — 예상된 항목).

이 앱은 안드로이드 버전과 동일하게 BMFKit("bstage") 하이브리드 커뮤니티/결제 SDK를 임베드하며, iOS에서는 WKWebView + bstage 스크립트 메시지 핸들러로 동일한 민감 브리지 표면(토큰·로그인·라우팅·결제·파일다운로드)을 노출합니다. 이 브리지가 핵심 점검 대상(F-1)입니다. 그 외 프레임워크로 Banuba(AR 뷰티필터, ML 모델 출처)·Amazon IVS(라이브)·gRPC/SwiftNIO+NIOSSL(통신)이 포함됩니다.

개선 권고 항목은 모두 중간~정보 등급입니다: 웹 콘텐츠 ATS 비활성, 브리지가 외부영향 콘텐츠를 로드하는지 검증, Firebase 키 제한 확인, 커스텀 스킴 입력 검증, 약한 해시 사용처 확인, 탈옥탐지 부재. iOS 하드닝(PIE·카나리·ARC)·암호화(CryptoKit/AES-GCM)·TLS 검증(SecTrustEvaluateWithError+핀닝 흔적)·키체인 접근성은 양호합니다.

03 상세 발견 항목

F-1 bstage WKWebView JS 브리지의 민감 표면 노출 Medium

MASVS-PLATFORM · CWE-749 · 위치: BMFKit.framework (bstage SDK)

증거
BMFKit은 WKWebView(UIWebView 아님)에 addScriptMessageHandler:name:로 bstage 핸들러를 등록하고, 안드로이드와 동일한 민감 액션 어휘를 노출합니다. 
// BMFKit.framework strings
WKWebView (×69)   userContentController/addScriptMessageHandler:name:
handler name: "bstage"   returns: bstage_access_token
actions: accessToken, refreshToken, requestLoginSdk, requestAppState,
         executeLaunchRouting / changeStage, externalLink, redirectUrl,
         fileDownload, iapProductId, deviceId
영향
WebView 안에서 JS를 실행시킬 수 있는 공격자는 window.webkit.messageHandlers.bstage.postMessage(...)로 인증 토큰(bstage_access_token) 탈취 → 계정 탈취, 임의 인텐트/외부링크 라우팅, IAP 트리거, 파일 다운로드를 앱 권한으로 수행할 수 있습니다. 안드로이드 F-1과 동일한 브리지 표면입니다.
완화·정황
관측된 로드 대상은 https://cdn.static.bstage.in/…, https://license-global.pallycon.com/…(DRM) 등 HTTPS 1차/파트너 도메인이며, UIWebView가 아닌 WKWebView 사용, 적절한 TLS 검증(아래 5장) 등은 위험을 낮춥니다. 다만 F-2(웹 ATS 비활성)·F-4(커스텀 스킴)와 결합되면 외부영향 콘텐츠가 브리지에 도달할 여지가 있습니다.
권고
브리지는 1차 HTTPS 콘텐츠에만 부착하고, 메시지 핸들러가 처리하는 origin을 화이트리스트로 강제하십시오. 토큰 반환 액션은 호출 origin 검증을 거치게 하고, WebView로 로드하는 URL(딥링크/외부링크 포함)은 host/scheme 화이트리스트로 검증하십시오. 실제 로드 URL의 출처가 외부 제어 가능한지가 등급 확정의 핵심 — 수동/동적 검증 1순위입니다.

F-2 웹 콘텐츠 ATS 비활성 Medium

MASVS-NETWORK · CWE-319 · 위치: Info.plist NSAppTransportSecurity

증거
NSAllowsArbitraryLoads = false   // 전역은 안전
NSAllowsArbitraryLoadsInWebContent = true
영향
전역 ATS는 유지되지만 WebView 콘텐츠에 한해 평문(HTTP)·약한 TLS 로드가 허용됩니다. F-1의 bstage 브리지와 결합 시, 평문으로 로드되는 페이지가 MITM으로 변조되어 브리지를 호출할 수 있는 경로가 됩니다.
권고
웹 콘텐츠도 HTTPS만 사용하도록 NSAllowsArbitraryLoadsInWebContent를 제거하고, 불가피한 도메인은 NSExceptionDomains로 한정하십시오.

F-4 커스텀 URL 스킴 입력 검증 권고 Low

MASVS-PLATFORM · CWE-939 · 위치: Info.plist CFBundleURLTypes

증거
CFBundleURLSchemes: [ "flozip" ]
영향
커스텀 스킴은 다른 앱이 동일 스킴을 등록(하이재킹)하거나 임의 입력을 전달할 수 있습니다. 스킴 파라미터가 검증 없이 bstage WebView 로드·로그인 흐름으로 전달되면 오픈 리다이렉트 등에 악용될 수 있습니다.
권고
가능하면 Universal Links로 전환하고, 들어오는 URL의 host/path/파라미터를 화이트리스트로 검증하며 호출 앱을 신뢰하지 마십시오.

F-5 약한 해시 원시함수 존재 Low

MASVS-CRYPTO · CWE-328 · 위치: main binary

증거
CC_MD5 (×2), CC_SHA1 (×2)   // CryptoKit/AES-GCM/SecRandomCopyBytes와 병존
영향
MD5/SHA-1은 보안 목적(서명·무결성·인증) 사용 시 취약합니다. 다만 캐시 키·ETag·서드파티 SDK 호환 등 비보안 용도일 가능성도 높아 사용처 확인 항목입니다. (DES/RC4/ECB는 미발견)
권고
보안 목적이라면 SHA-256 이상으로 교체하십시오. 비보안 용도라면 주석/문서로 의도를 명확히 하십시오.

F-6 탈옥/안티탬퍼 탐지 부재 Info

MASVS-RESILIENCE · 위치: 전체

관찰
메인 바이너리·모든 프레임워크에서 탈옥 탐지(Cydia/경로 검사)·디버거 탐지(PT_DENY_ATTACH) 흔적이 발견되지 않았습니다. 결제(IAP)·DRM·커뮤니티를 다루는 앱의 경우 탈옥 단말에서의 토큰/브리지 오용에 대한 방어선이 부족합니다. 취약점 자체는 아니며 위험 프로파일에 따른 하드닝 권고입니다.
권고
고위험 흐름(결제·토큰)에 탈옥/디버거/후킹 탐지를 추가하고, 탈옥 단말에서 민감 동작을 제한하는 정책을 검토하십시오.

F-7 로컬 저장 민감정보 확인 권고 Info

MASVS-STORAGE · CWE-312 · 위치: main binary

관찰
NSUserDefaults(×10)·UIPasteboard(×3) 사용이 확인됩니다. NSUserDefaults는 암호화되지 않은 plist이고 일반 Pasteboard는 다른 앱이 읽을 수 있으므로, 토큰·PII가 여기에 저장/복사되지 않는지 확인이 필요합니다. (키체인 접근성은 kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly로 안전하게 설정됨)
권고
민감 값은 키체인에만 저장하고, NSUserDefaults/Pasteboard에는 토큰·자격증명을 두지 마십시오.

06 방법론 및 한계

점검 방식: IPA(서명된 ZIP) 해제 후 LIEF 0.17로 Mach-O(암호화·PIE·카나리·ARC·프레임워크·엔타이틀먼트) 분석, plistlib로 Info.plist/엔타이틀먼트/프로비저닝 분석, 커스텀 시크릿 스캐너, strings 기반 코드 패턴 점검을 수행했습니다. 기준: OWASP MASVS / MASTG.

빌드 상태: 메인 바이너리 cryptid=0(미암호화) — 문자열·심볼·시크릿 분석이 전부 유효했습니다(App Store/TestFlight 암호화 빌드였다면 바이너리 분석 불가).

한계 1 — 정적 분석 전용: 동적/런타임 테스트(트래픽 가로채기, 후킹, 실기기)는 수행하지 않았습니다. F-1의 bstage 브리지 악용 가능성과 Firebase 키 악용 가능성은 런타임 로드 콘텐츠·서버 설정에 의존하며 별도 검증이 필요합니다.

한계 2 — 디컴파일 부재: iOS는 jadx 같은 깔끔한 소스 디컴파일러가 없어 strings·심볼·plist 중심으로 분석했습니다. 메시지 핸들러 내부 로직과 로드 URL의 정확한 출처 추적은 디스어셈블러(Ghidra/Hopper/IDA)나 동적 분석이 필요합니다.

권한 보유 자산에 대해서만 점검을 수행해야 합니다. 본 보고서는 방어적 개선을 위한 것이며 익스플로잇 코드를 포함하지 않습니다.
